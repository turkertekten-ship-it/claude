# Deep review of the web and GitHub stack

**Date:** 2026-08-28
**Scope:** `src/oodarag/util/http.py`, `src/oodarag/scrape/`, `src/oodarag/ingest/`,
`src/oodarag/util/{hashing,logging,ratelimit}.py`
**Result:** 128 defects fixed — 13 critical, 39 high, 54 medium, 22 low.
663 tests added, none touching the network.

## Why this was needed

That code was written in one pass and shipped without a single test. Nothing in
it had been read a second time. The headline number is not "128 bugs in bad
code" — most of it is careful and several of the fixes are refinements of
already-thoughtful decisions. It is what one pass looks like when nobody checks.

Three of the criticals meant the affected feature had **never worked at all**,
which is the strongest argument here: a defect nobody had noticed in code
everybody assumed was fine.

## The thirteen criticals

### Things that were simply broken

- **The GitHub connector crashed on every default run.** `log.info("github fetch
  complete", repo=self.slug, **counts)` — and `counts` contains `repo`. Every
  ingest with default resources ended in a `TypeError`.
- **The HTML extractor returned no links on any page with navigation.** Links
  were collected from the *pruned* tree, after nav, header, footer and aside had
  been deleted — contradicting the collector's own comment that "a crawler needs
  the nav it just discarded". A normal three-region page yielded `links=[]`, so
  the crawler could not discover anything from it.
- **The extractor also threw away most of the article** when paragraphs hang
  directly off `<body>` with no wrapper element. Scoring excluded `body` from
  candidacy, so the winner was a single `<p>` and every sibling was dropped: a
  five-paragraph page extracted to 32 words.

### Credential leaks

- **The GitHub token was written into the shared `HttpClient.default_headers`.**
  It was therefore attached to every request that client ever made, to any host,
  printed by the client's `repr` and by every dataclass holding one, and
  permanently injected into a caller-supplied client used for other traffic.
- **`paginate()` followed the `Link rel="next"` URL to any host the server
  named, with the `Authorization` header attached.** A malicious or compromised
  API response could name its own collector.
- **urllib's stock redirect handler copies every header onto the redirect
  target.** A 302 from `api.github.com` to a third-party host handed that host
  the bearer token. Verified against stock urllib; `_SafeRedirectHandler` now
  strips `Authorization`, `Cookie` and `Proxy-Authorization` on a host change
  and keeps them on a same-host redirect.

### Reachable from a link in a stranger's page

- **`urllib.request.build_opener()` silently installs `FileHandler`,
  `FTPHandler` and `DataHandler`.** `client.get("file:///etc/passwd")` read the
  local disk, so one `<a href="file:///etc/passwd">` in a crawled page was a
  local-file read. Verified: stock `build_opener()` does read the file.
- **The response cap bounded only the compressed stream.** A gzip bomb declaring
  a truthful 1 KB `Content-Length` passed every check and expanded without
  limit. Verified with a 200 KB payload that decompresses to 200 MB.
- **An off-site redirect carried the crawl off-site.** Scope, robots and pattern
  gates all ran against the *queued* URL and never against `resp.url` after
  redirects.
- **`urllib.robotparser` does not implement wildcards.** It matches with
  `str.startswith`, so `Disallow: /*.pdf$` and `Disallow: /a/*/secret` matched
  nothing and the crawler fetched exactly what the site asked it not to.

### Hangs and data loss

- **`TokenBucket.acquire(tokens)` hung forever when `tokens > capacity`** — a
  condition that can never become true, so the loop slept and re-checked until
  the process was killed.
- **`burst=0` produced a zero-capacity bucket**, so the first `acquire()` never
  returned. `HttpClient(burst=0)` from a config file deadlocked the pipeline
  before its first request.
- **`base.run` replaced the whole hash map with one run's yield**
  (`next_cursor["hashes"] = new_hashes or seen_hashes`), so any connector
  legitimately yielding a subset had every unseen document forgotten and
  re-emitted as new on the following run.

## What the rest looked like

The 39 high and 54 medium findings cluster into recurring shapes, and the shapes
are more useful than the list:

| Shape | Examples |
|---|---|
| A remote server controls a loop condition | pagination with no page ceiling; rate-limit waits with no bound; a frontier a link farm can fill |
| A cap applied at the wrong layer | bytes capped before decompression only; error bodies read unbounded; XML entities expanded after the byte cap |
| Hostile input reaching a parser that trusts it | `xml.etree` expanding a billion-laughs DTD; `urlsplit` raising `ValueError` on `http://[::1` and aborting a crawl |
| Identity conflated | `%2F` decoded into `/`; IDN, trailing dots and IPv6 hosts treated as distinct sites; lone surrogates collapsed to `?` |
| Optional HTML tags not implemented | `<td>a<td>b` collapsing a row to one column; a missing `</a>` swallowing every later link |
| Unbounded growth | the ETag map; the content-hash map; error lists carried in a delta |

## What this says about the method

Every one of these was found by reading, not by running. The test suite that
came out of it is the durable half, but it did not find the bugs — it pins them.

Two of the three "never worked" defects were invisible from the outside: a crawl
that discovers no links and a page that extracts to 32 words both look like a
thin site rather than a broken extractor. That is the argument for the
[retrieval evaluation harness](PLAN.md) landing before any tuning: without a
number, "the corpus is thin" and "the extractor is broken" are the same
observation.
